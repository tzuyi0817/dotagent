# 診斷 bug：先讓它轉紅

適用於第一眼看不出原因的 bug、flaky、兩個已知狀態之間溜進來的 regression、效能退化。一眼看得出的錯誤不必走這套。六個階段依序走，要跳過必須說出理由。

整個流程的重點只有一件事：**先建一個會在這個 bug 上轉紅的回饋迴圈，才准開始猜原因**。沒有迴圈就盯著程式碼推理，猜中是運氣，猜錯是常態。

貼出任何指令、輸出或擷取物之前先遮掉 secret：寫成 `<REDACTED>`，迴圈改讀環境變數，HAR 與 log 只引用帶訊號的那幾行。遮完不夠診斷就明說並向使用者要。

## 1. 建立回饋迴圈

這一階段值得花不成比例的力氣：要積極、要有創意、不要放棄。要的是一道**緊**的訊號：一道指令，在這個 bug 上轉紅、修好後轉綠。手段大致依這個順序嘗試：

1. 失敗的測試：Vitest 單元或元件測試、Playwright E2E，挑能碰到 bug 的最淺 seam（測試切入的邊界）。
2. 對 dev server 的 curl 或 HTTP 腳本。
3. 帶 fixture 的 CLI 或腳本，輸出與已知正確的快照比對。
4. Playwright 無頭腳本直接操作畫面，對 DOM、console、network 下斷言。
5. 重播擷取物：把真實的 request、payload、事件序列存成檔案，單獨餵進那條程式路徑。
6. 丟棄式 harness：只拉起最小子集（一個 composable、一個 store，mock 掉依賴），一個函式呼叫就碰到 bug。
7. 隨機輸入跑上千次，找「有時候輸出不對」的失敗模式。
8. bug 出現在兩個已知狀態之間時，把「切到狀態 X、檢查、重複」寫成腳本交給 `git bisect run`。
9. 同一輸入跑舊版與新版（或兩種設定），diff 輸出。
10. 最後手段：真的要人點，就給使用者一份精確的操作步驟，請他把輸出貼回來，你再據此推進。

有了迴圈還要**收緊**：能不能更快（快取 setup、跳過無關初始化、縮小測試範圍）、訊號更尖（斷言使用者的那個症狀，不是「沒有崩潰」）、更確定（固定時間、seed、隔離檔案系統、凍結網路）。三十秒且 flaky 的迴圈只比沒有好一點；兩秒且確定的迴圈是除錯的超能力。

**間歇性 bug** 不求乾淨重現，求把重現率拉高到可除錯：連跑一百次、平行跑、加壓、縮窄時序、插 sleep。50% 可以除錯，1% 不行。

**真的建不出迴圈**時停下來明說，列出試過的手段，向使用者要：能重現的環境、遮過 secret 的擷取物（HAR、log、帶時間戳的錄影），或在正式環境加暫時探針的許可。沒有迴圈就不進第二階段。

完成判準：能說出**一道已經實際跑過**的指令（附遮過的指令與輸出），它驅動真正的 bug 路徑並斷言使用者描述的症狀、每次結果一致（間歇性 bug 則重現率已固定在可除錯的高度）、幾秒內跑完、不需要人介入。發現自己在這道指令存在之前就開始讀程式碼建立理論，立刻停下：那正是這個 skill 要擋的失敗。

## 2. 重現並最小化

跑迴圈，看它轉紅。確認三件事：紅的是**使用者描述的那個**失敗，不是旁邊碰巧出現的另一個；多次執行都重現；精確的症狀（錯誤訊息、錯誤輸出、慢的數字）已記下來，之後才能驗證修法對準它。

接著一次砍一個條件：輸入、呼叫端、設定、資料、步驟，每砍一個重跑一次，只留砍掉就轉綠的那些。最小化讓第三階段的假設空間縮小，也直接成為第五階段的回歸測試。

完成判準：剩下的每個元素都是必要的，拿掉任一個迴圈就轉綠。

## 3. 提出假設

在測任何一個之前，先列出三到五個假設並排序。只想一個會錨定在第一個看起來合理的想法上。

每個假設都要可證偽，寫成預測：「如果 X 是原因，那麼改 Y 會讓 bug 消失、改 Z 會讓它更糟。」寫不出預測的只是直覺，丟掉或磨利。

排序後的清單先給使用者看，他常有能瞬間重排的資訊（「我們昨天剛改了第三個」）或已經排除過的假設。使用者不在時依自己的排序繼續，不卡住。

完成判準：三到五個帶預測的假設，已排序，已給使用者看過或已註明使用者不在。

## 4. 插探針

每個探針對應第三階段的一個預測，**一次只改一個變數**。工具優先序：能用 debugger 或 REPL 就用，一個斷點勝過十行 log；其次在能區分假設的邊界放定點 log；log 全開再 grep 是最後才考慮的事。

每條 debug log 加同一個獨特前綴，例如 `[DEBUG-a4f2]`，第六階段一個 grep 就清乾淨。沒加前綴的 log 會活下來。

效能問題不靠 log：先量基準（`performance.now()`、瀏覽器 Performance 面板、profiler、query plan），再 bisect。先量，後修。

完成判準：每個探針的結果都寫明支持或推翻哪個假設，且有一個假設存活、其餘被推翻。

## 5. 修復並加回歸測試

回歸測試寫在修法**之前**，但只在有正確的 seam 時寫。正確的 seam 是測試能重現 bug 在呼叫端真實發生的模式；只能測單一呼叫端、或單元測試重現不了觸發它的那條鏈，寫在那裡只會給假的安心。

找不到正確的 seam，這本身就是發現：程式碼的結構讓這個 bug 鎖不住，記下來。

有 seam 時：把最小化的重現改寫成失敗的測試、看它紅、套修法、看它綠，最後拿第一階段的迴圈對**原始未最小化**的情境再跑一次。測試斷言的是使用者的症狀，修的是實作，不改測試遷就實作。

完成判準：回歸測試在修法前紅、修法後綠；原始情境的迴圈轉綠；或已記下沒有正確 seam 的理由。

## 6. 清理

- 原始重現不再發生（重跑第一階段的迴圈）。
- 回歸測試通過，或已記下沒有 seam。
- 所有 `[DEBUG-…]` 探針已移除（grep 前綴確認）。
- 丟棄式 harness 與腳本已刪除，或移到明確標示的 debug 位置。
- 最後證實的那個假設寫進 commit 或 PR 說明，下一個除錯的人才學得到。

完成判準：以上每一項都勾過。
