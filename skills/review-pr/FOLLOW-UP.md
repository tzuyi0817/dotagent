# 追加審查：作者修正之後的那一輪

完整的證據鏈再跑一次，只改動候選來源與收尾。

- 在**步驟 1**，額外抓取先前的 review、意見，以及**每則意見的回覆串**：
  `gh api /repos/<owner>/<repo>/pulls/<n>/reviews` 與
  `gh api /repos/<owner>/<repo>/pulls/<n>/comments`（回覆帶有 `in_reply_to_id`，逐一歸屬到所屬的串）。
  先前每則阻擋意見都是**必查候選**：原本的問題修好了嗎，修法有沒有帶出新的問題？

- 讀 `<git-common-dir>/dotagent-review/pr-<n>/` 底下的每一輪記錄（步驟 8 寫的，號碼即輪次）。它與 API
  互補而非重複：API 只有送出去的意見，記錄還有 `withdrawn`（撤掉過的修法，步驟 7 判來回擺盪要用）與
  `head_sha`（本輪的量測基準）。

  **本人的 PR 只有這份記錄。** 這種 PR 從不 POST，`gh api` 抓到的 review 必然是空的。目錄不存在或為空才
  當作首輪，並在 body 講明沒有可對帳的前一輪——不要把「API 查不到」讀成「前一輪不存在」。

- **作者回覆之後，舉證責任在你身上。** 這種意見只有兩種處理方式：**接受並撤回**，或**在同一個串中以新證據反駁**。
  把作者明確拒絕過的意見原樣重送，讀起來就是根本沒看回覆。

- 在**步驟 2**，把 Finder 聚焦在增量 commit 與每個修法周邊。「宣稱 vs 實作」lens 仍然掃完整份
  `gh pr diff`，抓出夾帶在修正 commit 裡、沒有被宣稱的變更，例如 lockfile 或順手改的東西。

- **步驟 0 的規模判斷改用增量 diff**：`gh pr diff` 的總量不代表這一輪的工作量。以「上一輪審過之後的新
  commit」量測，基準取自最新一份記錄的 `head_sha`（本人的 PR 沒有別的來源）：
  ```bash
  git -C <repo> diff <上一輪記錄的 head_sha>..pr-<n> --stat
  ```
  但只要新進的變更碰到步驟 0 列的高風險領域，仍走完整流程。

- body 開頭寫**來源與規模**：新進的 diff 是照著意見做的小修，還是一次改寫？把每個發現標記為新程式碼、
  回歸、既有問題，或前一輪漏掉的。上千行的改版除了名字之外就是一個新 PR，發現變多是預期中的結果。

- 在**步驟 4 與步驟 8**，把先前每個發現對帳為已修復、未修復或部分修復，並在 body 附上驗證證據。
  新發現照常分流。

- 先前所有問題都已修復且沒有新的阻擋發現時用 `APPROVE`；否則依步驟 8 的規則選 event。
  即使是 approve，body 仍要逐項附上驗證證據。步驟 8 的送出前確認同樣適用。
  本人的 PR 照步驟 8 輸出到終端機，event 只在使用者要求送出時才需要決定，且一律 `COMMENT`。

完成判準：`dotagent-review/pr-<n>/` 的每一輪記錄都已讀入並納入對帳；先前每個發現都有本輪的裁決與證據；
作者回覆過的每則意見都已接受並撤回、或以新證據反駁；所有新變更都已檢查；投遞方式依步驟 8 判定，
需要 event 時它與殘留的阻擋狀態相符。
