# 邏輯分支：單檔 HTML 的狀態模型

一個自給自足的 HTML 檔（純 HTML/CSS/JS，不需安裝、不需 build、不需 server），任何人雙擊就能按按鈕驅動狀態模型。用在**業務邏輯、狀態轉換、資料形狀**這類紙上看起來合理、推到真實案例才發現不對的問題。問題若是外觀，走 [ui.md](ui.md)。

因為只有一個檔案，可以直接交給 PM、設計師或領域專家自己玩，所以整個頁面講他們的語言，不講程式碼的。

## 步驟

1. **寫下問題**。動手前用一段話寫清楚要驗證的狀態模型與問題，放在頁面可見的開頭，不只放註解。答錯問題的 prototype 是純浪費，之後也要能回頭檢查。
2. **把邏輯隔離成可搬走的模組**。真正回答問題的邏輯放在一個 `<script>` 區塊裡，寫成純模組，日後可以原樣搬進真實程式碼。形狀依問題選：
   - 純 reducer `(state, action) => state`：動作離散、狀態是單一值。
   - 狀態機：「現在哪些動作合法」本身就是問題的一部分。
   - 一組對純資料的純函式：沒有隱含的當前狀態，只有轉換。
   - 帶明確方法面的 class 或模組：邏輯真的擁有持續的內部狀態。

   選最貼合問題的形狀，不是最容易接到頁面的。保持純粹：不碰 DOM、`document`、按鈕 handler，頁面呼叫它，反向不行。這是 prototype 丟掉之後唯一留下的東西。
3. **做出可分享的頁面**。由上而下：
   1. 標題與一行說明（第 1 步的問題）。
   2. **目前狀態**：完整相關狀態，用有標籤的面板呈現，不是 JSON 原文；每次點擊後重繪，必要時標出剛剛變了什麼。
   3. **自由操作**：每個動作一顆按鈕，隨時可按、順序不限。
   4. **引導情境**：分頁式，每頁一個情境，上方一段白話說明這個情境設定了什麼、該注意什麼，下方是依序要按的按鈕，每顆都是真的動作。開始情境時重設到已知初始狀態。挑紙上難推的情境：正常路徑、刁鑽邊界、一個應該被擋下的操作。

   版面乾淨克制：清楚的字型階層、留白、一個強調色；沒有動畫，不搶狀態與按鈕的注意力。
4. **交出去**。傳檔案或直接 `open` 它。有價值的時刻是對方說「等等，這不該發生」「我以為 X 會不一樣」，那是**想法**裡的 bug。要加動作或情境就加，prototype 會演化。
5. **收尾**。驗證過的 reducer、狀態機或函式組搬進真實模組（決定已吸收）；HTML 外殼跟著整個 prototype 進 `prototype/<name>` 分支，單一檔案在那裡隨時能再跑。

完成判準：問題寫在頁面開頭；邏輯模組不含任何 DOM 參照；狀態面板、自由操作、至少三個引導情境都能用；對方不需要任何說明就能自己操作。

## 反模式

- 加測試。需要測試的 prototype 已經不是 prototype。
- 接真實資料庫。除非問題就是持久化，否則狀態放記憶體。
- 泛化。沒有「以後想支援 X 怎麼辦」，一個 prototype 回答一個問題。
- 邏輯和頁面糊在一起。純模組一碰 DOM 就搬不走了，頁面只是純模組外面的薄殼。
- 動用框架、bundler 或 server。一個對方雙擊的檔案；dev server 就不「可分享」了。
- 把 HTML 外殼送進 production。頁面是為手點而優化的，值得留的是後面的邏輯模組。
