# PR 描述的形狀

PR 描述回答 reviewer 的三個問題：改了什麼、怎麼證明它能動、合併了會怎樣。流程（以 `git diff <base>...HEAD` 看完整範圍、推送、建立）依 rules `git-workflow`，本檔只管 body 的形狀。

語言跟隨該 repo 既有 PR 與 commit 的慣例，無慣例時用繁體中文（台灣）。沒有鋪陳、沒有客套，每一節只留 reviewer 做決定需要的內容；用該 repo 的領域用語，不另造名詞。

## 模板

```markdown
## 摘要

<關聯 issue / ticket，有才寫>

<一到三句：做了什麼、為什麼。接著一個最小的視覺>

## 驗證

- **之前**：<截圖 / 輸出 / 失敗的測試>
- **之後**：<截圖 / 輸出 / 通過的測試>

測試計畫：<跑過什麼、reviewer 可以怎麼驗>

## 合併風險

**可逆性**：單向門 / 雙向門，<一句說明>

**影響範圍**：<一個詞>，<可能被連帶影響的東西>
```

## 摘要：挑最小的視覺

散文只寫一到三句，重點交給一個能一眼看懂的視覺。依「這個 PR 的重點是什麼」挑，通常一種就夠，很少需要三種以上：

| 重點 | 視覺 |
|---|---|
| 一段邏輯或演算法 | 偽碼，只寫分支與回傳 |
| 執行期的呼叫順序 | 呼叫樹，縮排表示呼叫 |
| 畫面結構 | 元件樹，標出帶狀態的 composable 與 package 邊界 |
| 檔案職責或大範圍搬移 | 淺層檔案樹，每個目錄一句職責 |
| 元件或服務之間的互動、資料流 | Mermaid sequence 或 flowchart |
| 重點是「改了什麼」而周圍形狀既有 | 上述任一種的 diff，`+` `-` 標在樹或偽碼上 |
| 大半是新的、省略會掩蓋歸屬或順序、reviewer 需要可複製的目標形狀 | 整段程式碼 |

元件樹的 diff：

```diff
 <AttendancePage>              apps/hr/src/pages/attendance/
   useAttendanceQuery()
   <AttendanceToolbar>
+    <ExportButton />           packages/ui
   <AttendanceTable>
+    <ExportProgressDialog />
```

偽碼的 diff：

```diff
 onSave()
-  寫入內容
+  if 內容未變更
+    回傳快取
+  寫入內容
+  清除快取
```

視覺緊貼著它要說明的那句話。只留回答當下問題所需的節點、props、狀態與邊界，其餘砍掉。

## 驗證：拿證據，不拿形容詞

- 畫面有變：之前與之後的截圖，RWD 受影響時各一組。這是最強的證據。
- 行為有變：測試輸出或 console 輸出。指出那一條之前紅、現在綠的測試，用一句偽碼說它測什麼。
- 「應該沒問題」「手動測過」不是證據；寫出跑了什麼指令、在哪個頁面做了什麼操作。
- 測試計畫寫成 reviewer 可以照做的步驟：指令、頁面、操作、預期結果。

## 合併風險：先講能不能回頭

- **雙向門**：revert 就回到原狀，例如純前端邏輯、樣式、新增的元件。
- **單向門**：合併後有東西回不去或要額外處理：資料遷移、刪除對外 API、改 storage 格式、改共用 package 的介面、發布套件。單向門要寫出回退方式，或為什麼不需要。
- **影響範圍**先用一個詞定調（單一頁面、單一 app、共用 package、全站），再列可能被連帶影響的：版面位移、RWD、其他 app 對共用元件的使用、i18n key、store 形狀、API 契約。改到 monorepo 的 `packages/*` 時，用 workspace 依賴圖找出所有使用端並列出。
